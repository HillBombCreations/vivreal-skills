## System knowledge

### Architecture
The five API Lambdas in the merged stack (`VR-CMS-API`, `allRoutes.yaml` generated from `cloudformation/*.yaml`): getCollectionInfo, createAndUpdateColObjects, createAndUpdateColGroups, handleMedia, createAndUpdateIntegrations (HTTP + inbound webhook receivers + the `EventQueue.fifo` SQS consumer, which routes on `messageType`: scheduled social posts, content go-live, AND the hourly scheduled social sync sweep, `integration-sync-sweep`). All five have WebSocket integration. Plus **`mediaExportWorker`** (2026-10-03, #224): invoke-only, no HTTP route and no `Events:` block, async-invoked by handleMedia's `requestMediaExport` (`POST /tenant/media-export`, polled via `GET /tenant/media-export/status`); streams every `media_files` row into a STORE-only zip in the group's bucket, `MaximumRetryAttempts: 0` with an OnFailure DLQ and NO DLQ consumer (a hard-killed job stays `running`; the portal calls 20 minutes without progress stalled). Plus **`PaymentsMoveWorkerFunction`** (v5, `cloudformation/payments-move-worker.yaml`): invoke only, fixed name `VR-CMS-API-PaymentsMoveWorker` because VR_Secure_API invokes it by name (see "Changing payment provider" below). Plus the commerce **snapshot** function, a SEPARATE stack (`cloudformation-snapshots/template.yaml`, `snapshot-stack.yml`). Memory and timeout values: read them from the fragment, never from here. All on `nodejs22.x` since 2026-10-02. Multi-tenant routing: tenant content routes to the placement STORED on the group, read back by `resolvePlacement(group)`. **Nothing derives a database from a tier**, and the function that used to is deleted from every repo. A per-group database named after a group slug is legacy drift, not the model. Every `/tenant/*` route takes the placement in the **`key`** query param (`handleTenantRoutes.js` reads `req.query.key` and gates it with `isRoutablePlacement`, because Mongo would happily create a database named `undefined`), EXCEPT the `Auth: NONE` webhook receivers (`/tenant/webhooks/{square,meta,stripe/{token},shopify}`), which find the group by a verified identifier and route by `resolvePlacement(group)`.

### Before you report an absence
Load `vivreal-workflow:verification-discipline`: a zero is only evidence once the same query returns a known hit. ### Known gotchas
- Every `/tenant/` route needs the `key` query param (the dbKey value, `pod_NN`). A missing or junk `key` is refused by `isRoutablePlacement` before any connect.
- **`errorHandler` is correct only in CONTROLLER position.** It sets `req.resData` and always calls `next()`. Inside `handleTenantRoutes` that is fine (the wrapper reads `req.resData` after `fn`). From router-level middleware mounted before the wrapper, the `next()` runs the controller anyway and it overwrites the error: the gate fails OPEN while still logging. Router-level middleware writes its own response. Test a gate by asserting the status on the wire and whether the controller ran, never that `errorHandler` was called.
- **A field the strict schema does not declare is dropped on write, silently.** The v2.9.8 webhook claim `state` was never stored until v2.9.9 declared it on both ledger schemas. A new persisted field needs a round-trip test through the REAL schema plus a control proving an undeclared field vanishes.
- **`preupload-*` keys live one day.** The tenant bucket's `ExpirePreuploadOrphans` lifecycle rule deletes them after 24 h; a save promotes the bytes to `groupObjects/<docId>/...` and deletes the source. A reference still on a `preupload-` key after that is permanently dead (S3 403 behind the media 302). Verify by diffing referenced keys against the bucket listing, never by looking at the page.
- July 2026 additions: Square P2 (squareWebhook + `updateFulfillSquareOrder` fulfillment, idempotency ledgers w/ 30d TTL, oversell-safe `$gte` stock decrement), Instagram DM/comments backend (comments live from Graph API, DMs DB-backed in `instagram_*` collections, HUMAN_AGENT 7d window), jimp image derivatives (JPEG/PNG at 320/640/1280, NOT WebP), `markActivated` lifecycle signal on first content create.

All handlers are identity-guarded now (`if (connObj[dbKey] === entry)` in `createTenantDb.js`). Signature if it returns: the first request after an idle gap past `maxIdleTimeMS`, reconnect-length duration, an immediate successful retry. Do not go looking at the data.
- **The module-map re-read is still the wider surface.** `handleTenantRoutes.js` keeps the handle `connect()` returns, but only for its own idempotency ledger; the services still re-read the mutable `dynamicDb[...]` map after more awaits, which a superseded teardown can empty. Count it with every spelling (`git grep -o "dynamicDb\[[^]]*\]" -- src`; `dynamicDb[key]` is most of it), never `dynamicDb[dbKey]` alone. The wrapper also refuses a `key` that is not the requesting group's own placement, so a caller cannot read another group's database by naming it.
- **Studio ordering must agree with Client API by construction (#172).** The CMS default sort is `objectValue.order` then `_id`, the same pair the public read uses. Items sharing a `createdAt` millisecond ordered "correctly" before only by an unspecified `$setUnion` tiebreak, so never copy `createdAt` ordering to either side.
- **Collection-name lowercasing.** `createMainDb` takes `collection` as the mongoose MODEL name; with no `collectionName`, mongoose lowercases and pluralizes it, so a camelCase registration silently splits from a service that pins the name (`domainOrders` vs `domainorders`). Always pass `collectionName`; two collections both carrying a schema's full index set is the tell.
- **`test/unit/bulk-import-refuses-subscribers.test.js` times out at 2000 ms on the FIRST full-suite run after `npm ci`** and passes every run after (cold module load). Re-run, then run the file alone as the tiebreaker; do not raise the timeout.
- **A 500 here empties a section in the Studio and the preview reports it honestly.** Before calling an empty state a data problem, read the live page for what should be there and the console for the 500.

### Scheduled social sync (2026-10-03 #225, hotfixes #228 and #229)
The full pipeline across repos (schedule, selection, re-hosting, disconnect purge, every failure signature seen so far, the Meta deauthorize hazard) is the `vivreal-knowledge:vivreal-social-sync` skill; load it for anything past this summary.
- **Mechanism.** ONE static `AWS::Scheduler::Schedule`, `ScheduledSocialSyncSchedule` (`${AWS::StackName}-scheduled-social-sync`, `rate(1 hour)`, ENABLED) in `cloudformation/create-update-integrations.yaml`, targets `EventQueue.fifo` (ARN from SSM `/vivreal/prod/shared/fifo-sqs-arn`) with Input `{"messageType":"integration-sync-sweep"}` and a CONSTANT `MessageGroupId` (`integration-sync-sweep`), so ticks serialize against each other. `services/handleSqsEvent.js` routes that `messageType` BEFORE its event-type guard, into `services/core/scheduledSocialSync.js` `runScheduledSocialSync`. RoleArn reuses `SchedulerExecutionRole`. Not one schedule per account: nothing is created on connect or deleted on disconnect.
- **Selection is stateless, re-queried every tick.** mainDb `groups` with `frozen != true` and an integration of a type in `SCHEDULED_SYNC_TYPES` (facebook, instagram, tiktok); placement through `resolvePlacement` (a `PlacementMissingError` skips the group, logged `social.scheduledSync.no_placement`); every account whose `status` is absent or `active`. An account `markSocialAccountExpired` has marked is never dialed again until an owner reconnects, which IS the back-off. LinkedIn is excluded on purpose (`sync/linkedIn.js` calls `/v2/ugcPosts`, which needs a scope Vivreal does not hold); X is out of the product.
- **Sequential, one account at a time, through `syncIntegrationData`**, the same upsert-by-external-id write the manual "Bring your posts across" button uses, so an overlapping manual sync re-upserts rather than duplicating. Never throws: a failed account waits for the next tick, it does not retry through the DLQ.
- **Deploy dependency outside this repo.** The stack's deploy role needs `scheduler:CreateSchedule/GetSchedule/UpdateSchedule/DeleteSchedule` on `schedule/default/VR-CMS-API-*`, Sid `CmsStackSchedules` in `vivreal-hq/packages/fleet-ops/deploy-role/cloudformation/deploy-role-permissions.yaml` (added 2026-10-04). Without it the deploy fails `ScheduledSocialSyncSchedule CREATE_FAILED ... not authorized to perform: scheduler:GetSchedule` and CloudFormation rolls the WHOLE stack back to `UPDATE_ROLLBACK_COMPLETE` (v2.14.1 did exactly this). The type is not taggable, so no `TagResource`. The per-object content-golive schedules are created by the app's own execution role at run time, a different principal, which is why they never needed this grant.
- **Failure signatures.** Read the CreateAndUpdateIntegrations log STREAMS (newest first, `get-log-events`), not `filter-log-events`, which returns false zeros on recent events (see the `vivreal-infra:vivreal-lambda-logs` skill).
  - Healthy: exactly one `social.scheduledSync.completed` line per hour carrying `targetCount`, `synced`, `failed`, `byType`. `byType` counts ACCOUNTS attempted per platform; `failed` mixes per-post failures reported by the adapter with whole accounts that threw, so a non-zero `failed` needs the `social.scheduledSync.account_failed` lines beside it to mean anything.
  - `Cannot read properties of null (reading 'find')` in `findScheduledSyncTargets`: mainDb was never connected, because an SQS-invoked path skips the Express middleware that connects it. Fixed in #228 (`await mainDb.connect()` first). Any NEW non-Express reader of `mainDb.DB.*` in this Lambda must do the same.
  - `SQS message missing event type, skipping` on a sweep message: the code SERVING predates the sweep routing. Check the deployed version or artifact, not `main`.
  - `account_failed` naming `(#12) deprecate_post_aggregated_fields_for_attachement`: the Facebook Page feed asked for a deprecated aggregated attachment field (caption, description, link, name, object_id, source, type). Fixed in #229 by reading the link off `attachments{media_type,media,url,unshimmed_url,subattachments}`. Only a Page whose feed has attachments fails, so one Facebook account erroring while another passes is this, not a token problem.
  - Re-host refusal `not a storable image type (video/mp4)` on an Instagram reel: the adapter stored the MP4 as the picture. Fixed in #229 (a VIDEO stores `thumbnail_url`; with no cover it stores the empty string, which the re-host pass counts as skipped). Covered by the PR's tests; as of 2026-10-04 no reel had been processed live since the fix, so it is not yet proven in production.
  - An account flipped to `expired` with a provider message like "user has not authorized application": a real revocation at the provider (the app was removed there), not a sync defect. Every later tick skips it until an owner reconnects.
  - Instagram tokens: VR_Secure_API renews a long-lived token inside its last 7 days and must hand CMS the RENEWED ciphertext (Secure v2.20.0). Before CMS v2.12.3 (#226) the sync sent providers the still-ENCRYPTED token and then marked the account expired while returning 200; an account expiring right after a sync is that family.
  - TikTok syncing zero posts with clean logs was unexplained as of 2026-10-04.
- **Purge of synced posts (2026-10-01).** `purgeSyncedPosts` deletes only SYNCED posts (they carry an external post id; an authored post is never eligible) and the copied pictures with them, on three triggers: the per-post `objectValue.mediaExpiresAt` (a post with none is untouched), a post gone at the platform (bounded by the OLDEST post the fetch returned, because the fetch pages; a fetch that returned nothing deletes nothing), and an owner disconnect via the invoke-only `POST /tenant/integrations/purgeAccount`. Alarmed: `<stack>-synced-post-purge-incomplete`, `-synced-post-sweep-failed`, `-synced-post-vanished-volume` (`cloudformation/alarms.yaml`).

### AWS Lambda best-practice alignment
- All functions on Node.js 22.x (`test/unit/runtime-node22.test.js` binds the claim to both templates); the five API functions carry WebSocket integration (`WS_ENDPOINT` + `WS_TABLE`).

### MongoDB consistency & performance
- Multi-tenant via `dynamicDb[dbKey]`. dbKey is the tenant DATABASE name STORED on the group, read back by `resolvePlacement(group)` and never computed from a tier. A slugified per-group database is legacy drift, not the model, and at least one of those has no group pointing at it.
- `groupID` on tenant objects is a STRING (not ObjectId).
- `archived` filter: use `{ archived: { $ne: true } }`, not `{ archived: false }`, many docs lack the field entirely.
- `collectionObj.refID` is a string. The indexes are DECLARED in `@hillbombcreations/schemas` (`collectionObjectSchema.js`, the `.index(` calls at the bottom): read them there rather than trusting a list. Two traps in them: `sparse: true` on a COMPOUND index indexes every document carrying ANY indexed key, so `collectionObj_refID_subscriberEmail_1` is a no-op (the bookings index uses `partialFilterExpression` instead), and re-declaring a built index name with new options fails `IndexKeySpecsConflict` on every cold start, silently.
- Bulk import: use `insertMany` with `ordered: false` for partial-failure tolerance.
- Versioning: increment `version` atomically with `$inc`, prune via tail-deletion bounded by `maxVersionsPerObject`.
- Audit log writes: separate collection `auditLogs`, indexed on `groupID + timestamp`.

### Changing payment provider (v5, contract F-C19)
- A product list carries `collection_groups.commerce { state: selling | paused | moving, provider, moveId, movedAt }` (strict sub-schema, NO default: absent means selling, and readers must treat it so). VR_Secure_API writes `paused` on "disconnect, keep my products"; the CMS move worker writes `moving`, then `selling`. Client API checkout refuses 409 `not_for_sale` unless the list is selling.
- When the owner connects the other provider, Secure invokes `VR-CMS-API-PaymentsMoveWorker` with `{ groupID, dbKey, moveId, from, to }` (`services/payments/movePayments.js`). Per product, idempotently: reuse or create the product at `to`, `$set` only identity paths (old ids under `objectValue.previousProvider[from]`), never stock, sale fields or photos, so a sale mid-move survives. The list is re-typed IN PLACE. A failed product still moves, with `move.state: 'failed'` and the "Needs fixing" badge; re-invoking the same `moveId` after the move finished retries only those.
- A currency mismatch is refused up front and nothing moves (the list goes back to `paused`). Signals: `payments.move.started/item_failed/finished/refused`; a hard failure lands on `vivreal-payments-move-dlq`; a list left `moving` is logged `payments.move.stuck` by `sweepStuckMoves` (run from CreateAndUpdateIntegrations' SQS handler). All alarmed in `cloudformation/alarms.yaml`.
