## System knowledge

### Architecture
Three repos, one product surface: **vivreal-site-renderer** (`@hillbombcreations/site-renderer`, GitHub Packages; publishing hits every live customer site) renders site config into pages; **Vivreal_Templates** is the universal Next.js customer-site app, every site's Amplify app builds the shared **`stable`** branch (per-customer branches are DEAD; releases via promote-stable, main→stable FF) and consumes the renderer; **Vivreal_Site_Migrator** hosts three modes, `/migrate` (live-site migration), `/template` (identity-kit instantiation), and live-site **restyle** tooling, plus `packages/site-loader`, the semver-pinned package VR_Secure_API's `instantiateTemplateWorker` runs in production.

### Known gotchas
- **Version truth**: the renderer version is `package.json` on `origin/master` (**this repo has no `main`**), and what a consumer actually runs is the consumer lockfile. Never a CLAUDE.md version header; that header lags on purpose. Releases can ride non-release commits, so read the file, not the changelog. Never push docs-only to renderer master: the publish workflow fires on ANY master push. And **a green workflow is not a publish**: the job runs `npm publish || echo skipping`, so confirm on the REGISTRY with `npm view @hillbombcreations/site-renderer version` before letting any consumer bump.
- **The release train** (any kit that ships renderer/site-loader surface): renderer publish → Templates renderer bump (`^x.y.z`, the caret FLOATS, treat the lockfile as the canary) → migrator adopts the version → capability manifest regen → manual `npm publish` of site-loader (the migrator has no CI; a push triggers nothing) → VR_Secure_API pins site-loader AND the renderer EXACTLY (no caret, a deliberate edit per release, because the worker bundles them as real files) and re-vendors the worker manifest with the migrator's `commands/regen-worker-manifest.js`, which packs the PUBLISHED tarball and refuses an unadopted version. Never regenerate capabilities from a local `dist`: it stamps a real published version onto unpublished work and every freshness test still passes. A stale capability manifest surfaces FALSE gaps.
- **Prove a renderer release by composing every stored page, before publishing.** The quality pass as merged to master (#83) would have removed 30 forms on 17 sites: an empty form or careers board composed to nothing. Caught by a compose diff over every stored page before publishing, not by the suite; fixed in #85 and shipped as 1.82.0. The fix is a registry contract, `nullOnEmpty: false` on the form, positions and article-toc layouts (`src/composition/resolveLeafData.ts`), so those keep their body when the bound collection is empty; layouts that still declare `nullOnEmpty: true` are dropped when empty, by design.
- **Templates contact form: the recipient comes ONLY from the site** (#181, 2026-10-04). `src/lib/contactRecipient.ts` resolves it from the site's own contact info via `SITE_ID`; the request body is never read for a recipient (it was an open relay that sent Vivreal-branded mail to any address). A site with no contact email sends no `contactEmail` upstream, which VR_Client_API accepts from v2.15.0.
- **Site chrome is read from the TOP-LEVEL site fields only** (`siteData` stopped spreading the stale `siteDetails.values` mirror, 2026-09-29), matching what VR_Secure_API writes and VR_Client_API now emits.
- **Templates lockfile regens drop optional transitives** (`@emnapi`, `sharp`) and block fleet builds, so never fix a lockfile by deleting `node_modules` + `package-lock.json` and reinstalling, and never `npm install` on Windows. Text-patch only the changed entry's `version`, `resolved` and `integrity`, confirm the optional-dependency count is unchanged, and prove it with `npm ci --dry-run` (the `package-publisher` agent's procedure).
- **A page format absent from Templates `COMPOSE_FORMATS` 404s** (the `/shop` and `/about-us` regressions). `ecommerce`/`showcase` are NOT format values, the storefront format is `products`; `templateType` is ignored at runtime.
- **AN ISR PAGE THAT NEVER PICKS UP AN EDIT WHILE `no-store` PAGES DO IS A CONFIG MISMATCH BEFORE IT IS A DATA PROBLEM (2026-09-16).** vivreal.io's home kept old copy through every save while `/pricing` and `/faq` updated at once. Cause: the site's stored Amplify buildSpec never grepped `SITE_RENDER_MODE` into `.env.production`, so `next build` prerendered `/` as ISR and the runtime ran `enforceDynamicUnlessIsr()` off; inside every regeneration `connection()` makes Next throw E132 and re-store the previous page with a 3 to 30 second revalidate. Failure mark on a `?og=<random>` probe: `HIT s-maxage=30` with an ETag that survives saves, or a save that never yields `MISS`. **A long run of `STALE no-store` alone is NOT a failure on Amplify compute**: fixed sites showed it for 30 seconds to over four minutes before `HIT s-maxage=300`, with clean compute logs (each request is a short Lambda invocation, so background regeneration likely only runs while requests arrive). The proof is a save that gives `MISS` with a new ETag within seconds. The `no-store` pages were never cached at all, because composed `/[slug]` formats read `searchParams`. Wrong leads chased first: page size, collection fan-out, "enable compute logs". Dougs Kitchen and The Comedy Collective had the same mismatch; all three fixed the same day. Check and fix: `vivreal-templates-knowledge` "ISR render mode" and `event-handler` (stored buildSpec). To prove a fix without a visible copy change, save a field that is in the payload but never displayed (an FAQ `authoredBy`) through the portal and watch for the `MISS`.
- **AMPLIFY COMPUTE FREEZES THE PROCESS BETWEEN REQUESTS, SO BACKGROUND WORK AND POOLED SOCKETS BEHAVE LIKE LAMBDA, NOT LIKE A SERVER (Templates #158, 2026-09-16).** A keep-alive socket to `client.vivreal.io` idle through a freeze failed on reuse in 67 to 148 ms (`write ETIMEDOUT`, `ECONNRESET` before TLS), which served degraded data and made `robots.txt` refuse for that request; `fetchWithReconnect` now retries idempotent reads whose `fetch()` rejects with a `TypeError`, at most twice. And `edgeSiteMap`'s wall-clock `setTimeout(abort, 800)` fired on thaw (33 of 40 aborts 1 to 194 ms into the next invocation), so quiet sites rarely refreshed their redirect map; `startAwakeTimeout` counts awake time only. Rule: no wall-clock timer around work that can outlive its request, and no assumption that a pooled connection survived idle. Compute logs live in `/aws/amplify/<appId>` (the `vivreal` app has none); count with Logs Insights.
- **An unknown layout renders as `CardsLayout`, silently.** `ContentRenderer.tsx` falls through `layoutMap[displayAs] ?? CardsLayout`, and site-loader never runs `checkRendererCompat`, so a binding naming a layout the PUBLISHED renderer lacks passes every check and ships a card grid. A strict enum fails the other way (`hero.variant` is a `z.enum`, so a loader missing the literal rejects the whole blueprint with a refusal that reads like a renderer-version problem). Check a `displayAs` against the published capability manifest, never the dist.
- **Revalidation, the three rules.** (1) A Studio save fires `site.updated` (Secure `emitWebhookEvent`), the delivery worker posts it to the site's subscribed `/api/revalidate`, and only that site's `site:<id>` tag drops; a DIRECT DB write skips all of it, so follow one with the same event (or one API page write). (2) Never call `POST /api/revalidate` by hand: a hard tag invalidation broke `robots.txt` at the origin and CloudFront cached the 500 for the whole host; the remedy is an Amplify `start-job --job-type RELEASE` on the same commit. (3) A revalidation clears only the compute instance that received it, with CloudFront on top, so after a BULK change rebuild the site (RELEASE) rather than trusting tags.
- **`SITE_RENDER_MODE` is a build input, not a runtime one.** The stored buildSpec copies it into `.env.production` in preBuild, so writing it changes nothing until that site rebuilds, and the fleet auto-syncs on the next Templates promote, activating every staged write at once. Pair each write with an observed rebuild of that one site. The discriminator is `x-nextjs-cache` PRESENCE, not `s-maxage`.
- **A demo or prospect site emits `noindex, nofollow` and NO canonical** (Templates `rootMetadata.ts`, owner decision W25-12a, 2026-10-10). It used to emit `meta.sourceUrl` as the canonical, which pointed a re-skinned demo at the real business it was copied from (and the kit demos at vivreal.io). The loader also refuses a demo `meta.sourceUrl` whose host is not on the prospects allowlist (`demoLifecycle.js`, `source_url_not_allowed`), so a donor URL fails at load. A stale `captures/<name>/load-state.json` sends `load.js` to UPDATE a site that no longer exists (`API error 400: {}`); move it aside.
- **An API-added page renders empty.** `POST /api/site/pages` stores no `blocks` (its validator accepts none), and Templates serves the route as a 200 with only nav and footer; Studio never hits this because it seeds `defaultBlocksForFormat` client-side. Follow an API add with a page update carrying explicit `blocks`, then check RENDERED markup, never a text match on the RSC payload.
- **Storefront wiring is format-agnostic** (`LIVE_PRODUCTS_OVERRIDES` + `collectBindingTargets`): a products binding on any composed format gets a working cart/PDP. Before that, non-`products` formats silently no-oped on Add/Buy.
- **site-loader multi-tenant rule**: collection dedup is TAG-SCOPED (0.2.1), without it a new site absorbs another site's collections on the same shared tenant DB. Layout capability hand-lists in `src/capability/composition.js` need a manual entry per new layout, regen alone is not enough.
- **BrandMark rule**: a brand logo is never center-cropped, wide wordmarks fall back to a letter-mark or favicon. Consumed by renderer chrome/cart, Templates cart dialogs, and the portal `SiteAvatar`.
- **Template sites are created on the Vivreal Content group** (key `vivrealcontent`), the hard template-flow rule.
- **The authored 301 map IS applied, on the not-found path only** (since 2026-08-18). The migrator persists `siteData.redirects`; Templates `src/lib/redirects.ts` `resolveMissingItemRedirect` answers a 301 from it in `[...segments]` and `[slug]/[itemId]` when nothing else serves the path. A path that resolves to a real page is never redirected, so a redirect "not firing" usually means the old path still renders something.
- **Studio-preview parity is deliberate seams, not identity**: preview shares the composition entry point with live but diverges on sample data and placeholder copy, never claim "what you see is what publishes."

- **The renderer must never emit an unsigned media descriptor as an image `src`, and the rule is written down.** `resolveConfigImageSrc` (`src/lib/sectionConfig.ts:131-165`) accepts two shapes: a bare authored string, and a CMS media descriptor with a signed `currentFile.source`. An **unsigned** descriptor (`{key,name}` with no `currentFile.source`, the shape between promotion and signing) deliberately resolves to `undefined`, because an S3 object key is not a URL and rendering it would emit a permanently broken `<img>`. `CapabilityTourLayout.tsx:1120` broke that rule from the other side: it declared `image: string` (`:952`) and guarded with a truthiness filter (`:958`) that an object passes happily, so React wrote `src="[object Object]"`, resolved against whatever page was showing. One document, one page, one site, and the layout's own comment at `:948-951` had predicted it.
