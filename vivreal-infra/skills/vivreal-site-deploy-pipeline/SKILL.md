# Vivreal Customer-Site Deploy Pipeline

How a site goes from "create" to "live on a custom domain." This is the AWS orchestration / **deploy-plumbing** view. For the site **product/data/authoring model** (pages, formats, site values, chrome, the publishDate gate, Studio↔live parity) see `vivreal-sites`. For EventHandler repo internals see `vivreal-eventhandler-knowledge`, for Templates internals see `vivreal-templates-knowledge`.

## The pipeline (AWS Step Functions, one Lambda per state)

State machine = Deploy-Site. **FOUR entry points start it**: `createSiteCollectionData` (mode `hosted_by_us`), `POST /api/deploySite` (blank first deploy), `redeploySite` (VR_Secure_API, since 2026-07-29), and `updateSiteEnvVars`'s rebuild (EventHandler, since 2026-07-29). Both of the latter previously did a direct Amplify StartJob with NO terminal-status writer, every such redeploy/rebuild hung `deploying` forever. Ordered states (each its own Lambda, deployed function names are `vh-${stage}-{name}`, the ASL Resource ARNs use `vh-site-deployment-{name}`; **typos are real, do NOT rename**):

```
SeedCollections → CreateGithubBranch → CreateAmplifyApp → StartAmplifyDeploy
→ WaitBeforeCheck (30s) → CheckAmplifyDeploy (poll) → DeployComplete? (Choice)
→ GetDefaultUrl → AssociateDomain? (Choice) → AssociateDomain (optional)
→ WaitBeforeCheckingDomain (30s) → CheckDomainAssociation → DomainAssociated? (Choice)
→ MarkLive | MarkFailed
```

- **`seedCollections`** (front state), lifted the (then ~17+) sequential CMS-API invokes out of the API Gateway 29s / Lambda 30s budget that was causing 504s. Reads `seed.{author,token}` + `templateType`, then writes collection groups/objects **directly to Mongo** (mainDb + tenant DB) via `@hillbombcreations/schemas`, **no CMS create endpoints** (`seedCollections/index.js`). Writes `pages`/`collectionGroups`/`integrationsUsed` back to the site doc. Failure → `markSiteFailed`; partial seeds cleaned by `VR_Secure_API/deleteSite`.
- **`createGithubBranch`**, despite the name, this is now **channel assignment only** (Phase 2, 2026-07-15): it resolves `CHANNEL_BRANCH || 'stable'`, creates **no git branch** and writes no marker file. Per-site branches are dead.
- **`createAmplifyApp` / `startAmplifyDeploy` / `checkAmplifyDeploy`**, creates the Amplify app pointed at the channel branch (`stable`), persists `deployment.branchName` on the site doc (schemas ≥1.21.0), sets `enableBranchAutoDeletion: false`, and triggers/polls the build.
- **`associateDomain` / `checkDomainAssociaion`**, optional custom-domain wiring via Route53. Two SEPARATE state machines handle domain acquisition: the domain-purchase saga (`docs/ops/domain-purchase-saga.asl.json`, newly registered domains) and the domain-transfer-in saga (`docs/ops/domain-transfer-saga.asl.json`, D3, charge-before-transfer, hourly poll loop, own `deploy-domain-transfer-saga.sh`, NO Amplify states; transfers keep the customer's nameservers verbatim and create no hosted zone, terminal status `transferred` not `live`).
- **`markSiteLive` / `markSiteFailed`**, terminal; sets `sites.deployment.status`. Initial status is `deploying` (`createSiteCollectionData.js`); the `POST /api/siteCollectionData` response returns `queued` (`controllers/createSiteCollectionData.js`); terminal is `live` (`markSiteLive/index.js`) or `failed`. No `pending` is ever written. `markSiteLive` also enqueues a push notification to VR_Main_API's `vivreal-notification-queue` on a template-instantiated site's first live deploy (runs after the critical DB write, 5s-raced, failures swallowed, never fails a deploy); its Lambda timeout is 75s. (A legacy `sync_conflict` value may linger on old docs; the template-sync webhook that wrote it was deleted in Phase 2, nothing produces it anymore.)

### State machine is NOT in IaC
**The state machines move only on a MERGE (EventHandler H11).** `serverless.yml` deploys no state machine; `.github/workflows/lambda_api.yml` applies all three ASLs from `docs/ops/` (and the execution role's inline policy) through `scripts/update-state-machine.sh`, `deploy-domain-purchase-saga.sh` and `deploy-domain-transfer-saga.sh`. A laptop `serverless deploy` leaves them as the last merge left them, so an ASL edit is a silent no-op and a new step is uninvokable. `npm run check:state-machines` is the read-only drift check. CI deploys with `--stage site-deployment`, so the step Lambdas are `vh-site-deployment-<step>`. The Deploy-Site state machine pre-dates the serverless setup; VR_Secure_API invokes it by a static ARN (`STATE_MACHINE_ID`, `hb-api-secrets` is RETIRED; secrets Phase 2 moved everything to `<secret-prefix>/*` Secrets Manager + `<ssm-prefix>/*` SSM, and the ARN also resolves from an SSM param EventHandler reads as `DEPLOY_STATE_MACHINE_ARN`). Source of truth = `Vivreal_EventHandler/docs/ops/deploy-site-state-machine.asl.json`, pushed by `scripts/update-state-machine.sh` (idempotent; CI runs it after `serverless deploy` on `main`). **Console edits are drift and get clobbered.** (`update-state-machine.sh` covers Deploy-Site only, the domain purchase/transfer sagas ship via their own `deploy-domain-purchase-saga.sh` / `deploy-domain-transfer-saga.sh`.)

## Amplify customer sites: how they build

- Each customer site = its own Amplify app, and **every app builds the shared `Vivreal_Templates` `stable` branch** (Phase 2, 2026-07-15, Templates has only `main`, `stable`, and dev PR branches). The build renders via `vivreal-site-renderer` against live CMS/Client-API data; per-site identity comes from the injected env vars, not from git.
- **`createAmplifyApp` injects build env vars** so the branch builds against the right tenant: `API_KEY`, `SITE_ID`, `NODE_AUTH_TOKEN` (PAT for `npm ci` against GitHub Packages), `NEXT_PUBLIC_SENTRY_DSN`, optional analytics vars, and the optional cache-invalidation pair `SITE_CACHE_TTL_SECONDS` + `REVALIDATE_WEBHOOK_SECRET`. A var only reaches the app if it is also grepped in the buildSpec allowlist (`src/shared/amplify/buildSpec.js`). **`BUCKET_NAME`, `CDN_BASE_URL`, collection-group IDs (`SHOWS_ID`, …), and `STRIPE_SECRET_KEY` are NOT injected.** Written to `.env.production` in Amplify's `preBuild` phase.
- **The allowlist that matters is each app's STORED buildSpec, not `buildSpec.js`** (2026-09-16). Editing `src/shared/amplify/buildSpec.js` changes no existing app; only `createAmplifyApp` (create, and UpdateApp on each state-machine redeploy), the `updateSiteEnvVars` self-heal and `scripts/backfill-revalidate-webhooks.js --execute` rewrite it. A key present in the Amplify env but not grepped is visible to `next build` and invisible to the running server: `SITE_RENDER_MODE=isr` built vivreal.io's home page as ISR that the runtime could never regenerate, so edits never showed there until a rebuild (Example Diner and Example Comedy Club had the same gap). Before trusting any env var to reach a site, read `aws amplify get-app --query app.buildSpec`. Fix procedure and fleet state: `vivreal-eventhandler-knowledge`, "Stored buildSpec".
- **Per-site cache-invalidation provisioning**, when `SITE_CACHE_TTL_SECONDS` is set, each deploy mints a per-site `REVALIDATE_WEBHOOK_SECRET` and auto-upserts a `webhooks` subscription so on-publish revalidation works out of the box (`createAmplifyApp/index.js`; gated via `serverless.yml`).

## Releases: the promote-stable workflow (Phase 2: 2026-07-15; build tiers since v7, 2026-10)

**Merging/pushing `Vivreal_Templates` `main` does NOTHING to customer sites.** To release: dispatch the **promote-stable** workflow (`promote-stable.yml`, `workflow_dispatch`; a real promote runs from `main` only, while a dry run passes the branch guard from any ref though the AWS role still refuses a non-main ref; inputs `scope` (`live` default, or `all`) and `dry_run`; GitHub App auth for the push). Its order is load-bearing: it assumes the AWS role first, then fast-forwards `main` → `stable`, then `scripts/fleet-build.mjs` starts one Amplify RELEASE build per app pinned to the promoted commit, **for the `live` build tier only**. Source: the header comments of both files on Templates `origin/main` (cost cut V7.247).

- **Tiers.** Each app's tier is its `vivreal:buildTier` tag: `live` (paying customers, Vivreal-owned sites), `demo` (showcase sites) or `qa` (scratch). An untagged app, or an unknown value, counts as `live`, so a missing tag costs a build and never leaves a customer behind.
- **Demo sites catch up weekly** in `demo-catchup.yml`, which builds `stable`'s head and never moves `stable`. Run it by hand before a walk or a reshoot. `scope: all` on the promote builds every tier (a security fix).
- **Recovery.** If the fan-out fails or reports an app busy, dispatch `demo-catchup.yml` with `tier: live` (or `all`). **Never re-run promote-stable to recover**: it re-reads `main` and moves `stable` again to whatever has merged since.
- **Autobuild.** New apps are created with `enableAutoBuild: false` and a build-tier tag (EventHandler `createAmplifyApp`, v7). An older app may still have git-push autobuild on, which builds it from the push as well; fleet-build skips an app already building the same commit.
- **Scope of the fan-out.** fleet-build lists apps through `ListApps` in one account and one region (`--region`, default `us-east-1`). An app hosted in another account (the cross-account site) is outside it, so check how that app builds before assuming a promote moved it.

So: renderer change → publish renderer package → bump the exact pin on Templates `main` → merge → **dispatch promote-stable** (dry run first) → the live tier builds → live. (The renderer publishes via its own CI on push to its `master`.)

- **Per-site emergency hold:** keep the app's auto-build off and leave it out of the fan-out (its tier), then use an explicit `start-job` to release it later.
- The old "Sync main to site branches" workflow, per-site branches, `/sync-templates`, and the `templateSyncWebhook`/`POST /createBranch` endpoints in VR_Secure_API are all **deleted**. VR_Secure_API resolves a site's branch via `resolveSiteBranch(site, group, templateTypeOverride?)`, persisted `deployment.branchName` first, legacy `${group.key}-${site.key}-${templateType}` naming as fallback (no un-migrated sites remain).

## Debugging a stuck / wrong site

- **Stuck `deploying`** (the in-flight status; the API response says `queued`) → inspect the Step Functions execution for the failed state; check `checkAmplifyDeploy` (build failed) or `checkDomainAssociaion` (domain not yet associated).
- **EVERY new-site deploy failing at `CreateAmplifyApp` with an opaque ValidationException** → the GitHub installation token blew Amplify CreateApp/UpdateApp's 255-char `accessToken` cap (GitHub's 2026 stateless rollout mints ~520-char tokens). `getInstallationToken.js` forces the classic ~40-char format via `X-GitHub-Stateless-S2S-Token: disabled` and throws if a minted token exceeds 255 chars, if this resurfaces, GitHub has likely sunset the override.
- **`failed`** → `markSiteFailed` ran; read the execution input/output and the failing state's logs. Re-create via `createSites` after fixing.
- **"My Templates/renderer change isn't on the live site"** → either (a) you merged to Templates `main` but never ran **promote-stable** (merging main alone releases NOTHING), (b) the renderer package wasn't published/bumped, (c) the site's app is in the `demo` or `qa` tier and waits for `demo-catchup.yml`, or (d) its release job has not finished.
- **"Content created in portal missing on site"** → that's the publishDate storefront gate, not the deploy pipeline, see `vivreal-db`.
