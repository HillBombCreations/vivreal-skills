## Cross-tenant IDOR fix pattern (E15) + prod-bug punch list

Any new mutation route must scope BOTH layers. `errorHandler` now forwards `err.code` as `errorCode` on non-5xx responses, the portal's CancelFlow retention-offer UI depends on reading it. ## Tier quotas: the sentinel scheme, the capability flags, and the AI agent

Quotas live in **`@hillbombcreations/tier-quotas`**. **Sentinel scheme: `-1` unlimited, `0` no access
(fail closed), `>0` a cap**, read through `isUnlimited(<0)`, `hasAccess(!== 0)` and
`getEffectiveLimit`. The old `isUnlimitedQuota(0) == unlimited` inversion is gone, and `0` now
genuinely denies rather than sitting as a dead gate.

**Read the tier ladder and every quota number from `src/tierQuotas.ts` on the package deployed
line. Do not quote one from here, and do not trust a remembered one.** Three things have moved
under this file before: a tier was retired and folded into another, the alias table that used to
forgive its old spellings was then deleted (so a retired tier id now normalises to `free` rather
than erroring, which is a silent downgrade rather than a crash), and the agent-action allowance
changed by an order of magnitude in one release. A stored group document still carrying a retired
tier id is the case to think about: nothing rewrites it when a package folds a tier.

## Multi-tenant routing: `dbKey` (NOT `key`)

**Secure reads `req.query.dbKey`**, CMS reads `key`. The portal proxy must set `dbKey` explicitly for Secure routes. `dynamicDb.js` pools per-tenant connections (`maxPoolSize=3`). mainDb `Vivreal` holds group metadata. **Never filter mainDb by `groupName`**, use `{ _id: ObjectId(groupID) }` (shell form; in Node write `new ObjectId(groupID)`, bson 6 throws without `new`). `{ key }` takes the group's slug, never `dbKey`: `dbKey` is the tenant database name (`pod_01`, `pod_02`), no group's `key` equals it, so `{ key: dbKey }` returns null.

## Adding a route: 7 steps (step 7 = the 502 trap)

1. `services/foo.js` → 2. `services/index.js` → 3. `api/controllers/foo.js` (set `req.resData`) → 4. `api/controllers/index.js` → 5. `scripts/validators.js` (Joi) → 6. `api/index.js` (`handleHBRoutes`) → **7. `cloudformation/<lambda>.yaml` API Gateway event**.

**Step 7 is a hard rule.** Secure (like CMS + Client) registers **one explicit API Gateway event per route**, there is **no catch-all `{proxy+}` integration**. An Express route the gateway has no event for is unreachable: the request falls through and fails, **502** post-deploy here (CMS surfaces the same miss as a 403; Client rejects it at the edge). Always add the event in the `cloudformation/` fragment; `cloudYamls/allRoutes.yaml` is generated by `scripts/merge-template.js`, never edit it directly. (Cross-repo rule + why Main API is exempt: `vivreal-lambda` deploy reference + `vivreal-auth-architecture`.)

## Billing specifics

- **Downgrade preflight** (`GET /api/billing/preflightDowngrade`), recounts `collection_objects` + `webhooks` via tenant connection, compares to target tier quotas, returns `{ ok, violations[], currentTier, targetTier }`. Downgrade to a 0-access target (e.g. free's `webhooks`/`agentActions` 0) is now a preflight violation. Re-used by `createCheckoutSession` as a defence-in-depth gate (400 with violations on reject). Opportunistically heals `entries.totalSize` drift.
- **Cancellation** (`handleSubscriptionEnd.js`), demotes to `free` (it no longer writes the 6 tier-driven quota fields, they derive live from the tier), sets `frozen:true` + persists `overQuotaSinceCancellation {violations, setAt}` when over-limit; `getGroupInfo` serializes it → drives the portal frozen/over-quota banner. Webhook-order safe: lookup by `stripeSubscriptionID` misses (no-op) when cancellation is the side-effect of an in-progress tier change.
- **Stripe portal lockdown**, optional `STRIPE_PORTAL_CONFIGURATION_ID` disables `subscription_update` so tier changes route through the preflight-gated Manage Plan page. Bootstrap is a manual one-time script.
- **Overage billing**, new paid subs **auto-enroll** `overageBilling.enabled` + the tier default spending cap (`DEFAULT_SPENDING_CAP`; grandfathered if the prior tier was overage-eligible, enterprise excluded); toggle via NEW **`PUT /api/group/overageBilling`** (`toggleOverageBilling.js`, native-driver persist). `createCheckoutSession` discloses overage + cap in Stripe `custom_text`. `handleInvoiceCreated.js` adds Stripe invoice items at the tier-quotas `OVERAGE_RATES` (CDN $0.50/GB, API $0.005/call, agent $0.05/action); the `overageBilling.lastInvoice` snapshot persists via the native driver, and a **deterministic per-(invoice,bucket) Stripe idempotency key** stops duplicate charges on `invoice.created` retries; fails safe (undercharge not overcharge). The old "`overageBilling` + `stripeSubscriptionID` UNDECLARED in strict `groupSchema`" gotcha is **RESOLVED by schemas 1.27.0**, which declares `dbKey`, `stripeSubscriptionID`, `subscriptionStatus`, `subscriptionCadence`, `currentPeriodEnd`, `overageBilling{enabled,spendingCap,lastInvoice}`, `scheduledTierChange`, `cancellation`, `pauseCollection`, `retentionDiscount`. The native-driver write is retained DELIBERATELY (`spendingCap` is Mixed with dynamic `bucketCaps.<bucket>` keys), not because of stripping. `featureFlags` is declared in schemas 1.29.0 (strict:false sub-schema, only `aiActionsEnabled` declared), though `updateFeatureFlags.js` still writes via the native driver.
- **Cancel flow + retention (Phase 3)**, `billingAndSubscription/services/subscription/{cancelSubscription,pauseSubscription,reactivateSubscription,applyRetentionDiscount}.js`, gated by `requireGroupBillingRole.js`; routes `POST /api/billing/{cancelSubscription,pauseSubscription,reactivateSubscription,applyRetentionDiscount}` + `releaseScheduledChange`. Cancellation is **period-end, never immediate** (`cancel_at_period_end` + `cancellation.{requestedAt,effectiveAt,reason,feedback}`; demotion happens in `handleSubscriptionEnd`). **Pause does NOT set `frozen`** (D9; `frozen` is the end-of-subscription state, and VR_Client_API serves a frozen site READ ONLY through `frozenPolicy.js`, refusing checkout, contact forms and writes); CMS blocks writes on a future `pauseCollection.resumesAt` (`GroupPaused` 403). One pause per 12 months, anchored on `pauseCollection.lastPausedAt`. Retention: coupon `retention_save_30_3mo` (30% off, repeating 3 months), `RETENTION_COUPON_ID` via SSM `<ssm-prefix>/shared/stripe-retention-coupon-id`, once per group guarded on `retentionDiscount.appliedAt` (NOT Stripe's discount list, that only reports currently-applied discounts); deliberately no `max_redemptions`. NY GBL 527-a imposes an advance-notice obligation before any price change.

## Admin routes and IAM proof

- **Two Cognito pools, and an HTTP route binds to ONE.** The `/api/admin/*` routes (count the `Path: /api/admin` events in `cloudformation/`, never quote a number: they sit in `getGroupInformation.yaml` and, for the four admin push routes, `userAndAuth.yaml`) use `MyAdminCognitoAuthorizer`, the dedicated admin pool (`Vivreal-Admin-Identity`, MFA), so a customer-pool token is rejected at the gateway there. **One exception on purpose:** `PUT /api/admin/groups/{groupID}/prospect` takes the DEFAULT (customer pool) authorizer, because the site loader signs in there and sends no `x-user-ctx`; its controller gates on `ADMIN_EMAILS`. Read each event's `Auth` block before assuming the pool. `PUT /api/group/featureFlags` accepts either pool; every other route inherits the customer pool.
- `iam simulate-principal-policy` on the role (the granted actions `allowed`, a control `implicitDeny`) is only a PRE-CHECK: a simulation evaluates the resource ARN and context keys you hand it, and twice in v7 it passed grants the real call then denied. The proof of a grant is the first real call (`vivreal-infra:vivreal-iam-secrets`).

## v7 to v7.2 (live 2026-10-20/21, tags v2.22.1 to v2.22.6)
- **The business time zone (v7.1).** `PUT /api/group/timezone` (UpdateGroup, `setGroupTimeZone`) lets an admin or the owner set `groups.timezone`. Every write is a compare-and-set on `expectedTimezone`, the zone the caller last saw (`null` for none), so the portal's automatic first save never replaces a zone someone already set; a lost race answers the stored zone with `applied: false`. `createGroup` stores a zone at creation too. Both go through `canonicalTimeZone` (`src/shared/timeZone.js`: canonical IANA name, `UTC` accepted, fixed offsets refused, `InvalidTimeZone` otherwise), the same rule VR_Client_API serves with. The write is verified by reading the field back, because a stale strict schema strips it silently.
- **Kit sample zones are scrubbed at instantiation (v7.1).** `scrubKitZones` in `src/shared/kitIdentity.js` removes the kit's `timezone` from every page's `labels`, `labels.openingHours` and each binding's `sectionConfig`, so a customer site inherits its business zone instead of the kit's city. It runs beside the contact scrub, before the name gate, and is skipped for the demo tenant (`keepKitContact`); the worker's log reports `zoneFields`.
- **Parked-domain sign-ups are one step (v7.2).** `src/parkedSignups/services/recordParkedSignup.js` saves a capture `subscribed` with `consentSource: 'capture'` and `objectValue.source` `parked:<domain>`; a hard bounce or complaint on the platform suppression list is still recorded but with a non-sendable status and `suppressedAt`, and an unreadable list writes nothing and returns the message to the queue. - **Site delete keeps people and shared lists (S9-D6, owner 2026-10-20).** `src/createSites/services/deleteSite.js` (`cleanupSeededCollections`): "this site's" lists are the union of four shapes, the site's `collectionGroups` manifest, the content and integration bindings read through `pageBindings`, and the groups in this business tagged exactly `site:<this site's _id>` (the provenance tag seeding writes; needed because a kit site's manifest is always empty). A people list (`PEOPLE_LIST_ROLES`: subscribers, contact, reservations, quote-requests, bookings, group-subscribers) is KEPT with every item while it holds anyone, whatever `deleteContent` says, because those are real people's details and a sign-up list is also the suppression record; an empty one goes. Usage rows are matched under both `collection_<id>` and `collectionObject_<id>`. Do not widen the union: unreferenced lists are live working data.
- **A rename rewrites kit-shaped titles only** (`src/shared/renameIdentity.js`, used by `updateSiteValues` and the agent's site tools). `seo.metaTitle` and `detailPage.seo.titlePattern` change only where the old name is the WHOLE title or a whole segment at either end joined by a kit separator (a pipe, a middle dot, a comma or a colon, each with its spaces), exact match after trimming. The title write is a native-driver write after the Mongoose commit, because the schemas package does not declare those paths.
- **Audit rows carry `expiresAt`** from the group's tier (`src/shared/auditLog.js`, the same `resolveExpiresAt` semantics as VR_CMS_API), reaped by the schema's TTL index; rows written before it have none.
- **`PUT /api/admin/groups/{groupID}/billing-source`** (admin pool; `adminSetBillingSource.js`, `setBillingSource.js`) writes `billing.source`, the comped marker. Count paying customers by `stripeSubscriptionID`, never by tier.

## Site page routes (v6)

- `POST /api/site/pages`, `PUT /api/site/pages/reorder`, `PUT /api/site/pages/{pageSlug}`, `DELETE /api/site/pages/{pageSlug}` on UpdateGroup (the `/api` prefix is required: Express mounts `/site/pages`, the gateway declares `/api/site/pages`). Each reads the site projected and lean, scoped by `{ _id, groupID }`.
- **The update allow-list comes from the schemas package's `pageFields`** (`updatePageValidator`), the union of every key stored on a prod page; a new page field needs a line there and nowhere else. Send each touched top-level page field WHOLE: the service writes `pages.$[elem].<key>`.
- **One page order rule**, `src/shared/pageOrder.js`: `order` is an integer `>= -1` on add, update, `/sites/update` and both site-create paths (`-1` is the home page sentinel). PageSchema declares `order: Number`, so junk would be a CastError 500; each path refuses it as a 400. Add requires `order` and accepts no `blocks`, so an API-added page renders empty until an update writes them.
- **Reorder persists now** (it was stripped by `bulkWrite` before the schema declared `order`), refuses an unknown slug with 404 before any write, and returns only slugs and orders. **Nothing calls it yet** (no caller in the portal's `src`, VR-MCP-Server or the migrator). **Known trap, fix on the next list:** its controller calls `errorHandler`, which always calls a plain `next()`, so Express falls through to `PUT /site/pages/:pageSlug` with `pageSlug = "reorder"` and a refused reorder runs the page-update handler.

## Write-path traps

- **Dotted and `$` body keys never reach a handler** (`express-mongo-sanitize` in `src/shared/createApp.js`), so `updates: { 'hero.title': ... }` arrives as `{}` and the update 500s on an unused array filter. Send whole top-level fields.
- **`updateSiteValues` MERGES `siteDetails.values`**: an absent key is untouched and an explicit `null` clears ("THE WRITE CONTRACT" at the top of the file). It replaced the `PRESERVE_ON_REPLACE` allowlist after four losses. Its unconditional `domainInformation` `$set` is safe only because Mongoose strips `undefined` during cast. After any site write, re-read the whole document and diff it against a pre-write backup.
- **An undeclared tenant-db model is `undefined`, not unbound.** Each Lambda's main-db map declares its own models (`instantiateTemplateWorker` declares only `siteTemplates`), so `mainDb.DB.groups` there is a `TypeError`, and a mock carrying both models passed 100% coverage over a line that could never run. Read the worker's own models map first; assert `Object.keys(mainDb.DB)` against the real map in a test.
- **`errorHandler` is correct only in controller position** (it always calls `next()`). Router-level middleware writes its own response.
- **A handled 4xx/5xx is a SUCCESSFUL Lambda invocation** under serverless-express, so `AWS/Lambda Errors` never moves. Alarm on the `<Function>.failed` literal `errorHandler` logs on every handled 5xx, paired with an API Gateway 5xx alarm for throttled requests that never ran.
- **`preupload-*` keys live one day** (`ExpirePreuploadOrphans`, set in `createBucket.js`). A save promotes the bytes to `groupObjects/...` and deletes the source; anything still referencing a `preupload-` key after that is dead.

## Lambda and MongoDB checklist (ported from the `secure-api` expert agent, 2026-10-20)

The expert agents are no longer loadable as skills, so the review checklist an agent without an
`Agent` tool used to load from them lives here. Query rules (tenant scoping, the mainDb `_id`
lookup, the `publishDate` and `archived` filters) live in `vivreal-knowledge:vivreal-db`, and
packaging and limits in `vivreal-infra:vivreal-lambda`; they are not repeated here.

### AWS Lambda best-practice alignment

- One deploy artifact per function, each with its own CloudFormation fragment and its own `build-lambdas.js` roster entry; a function missing from the build roster fails packaging, not tests.
- Stripe SDK initialization must be top-level, reused across warm invocations.
- IAM least-privilege: each Lambda must have only the policies it needs.
- WebSocket: agent, createAndJoinGroup, createSites and updateGroup carry `WS_ENDPOINT` + `WS_TABLE`. Send-message paths must be idempotent on stale connections.
- Step Functions integration: use `StartExecution` ARN format, NOT `DescribeExecution` ARN format (different IAM resource types).
- Cold start: billing Lambda's webpack bundle is the largest (Stripe SDK is heavy), measure and consider Provisioned Concurrency if p99 cold-start exceeds 3s.

### MongoDB consistency & performance

- Profile switch atomically updates `activeGroupID` on the user doc and re-issues the `active_ctx` JWT, verify the order doesn't leak across requests.
- Group creation: insert + S3 bucket creation must roll back together on partial failure (idempotent retry).
- Index audit: `groupID`, `userID`, `stripeSubscriptionID`, `cognitoSub` must be indexed; `groupID + userID` compound index for membership queries.
