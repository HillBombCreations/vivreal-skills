# VR_Main_API: knowledge digest

Last synced: 2026-10-21 against `origin/stable` (tag v2.15.2, the v7.2 hotfix line; read the tag)

The public-facing API: the **only unauthenticated-flow backend** (login, register, password reset, claim, email). Maps to `NEXT_PUBLIC_MAIN_API`. Express + serverless-express on Lambda (Node 22 on every function, arm64; `sam-template.yaml` `Runtime: nodejs22.x`), JavaScript, MongoDB + DynamoDB (WebSockets), Cognito, SAM. Read `${VIVREAL_REPOS}/VR_Main_API/CLAUDE.md` for the full route list (refreshed 2026-10-02).

## Architecture: the functions (re-derive the roster from `sam-template.yaml` on `origin/stable`)

Since v7 the roster also carries `SubscriberConfirmFunction` and `SubscriberConfirmResumeFunction` (V7.221, below). `ExpressLambdaFunction` (the monolith app, one greedy `/{proxy+}` route, no authorizer), `EmailConsumerFunction` (SQS consumer that does the actual SES sends), `EmailEventsFunction` (consumes SES events for transactional and lifecycle mail and writes the global `suppressions` list), `CampaignSendFunction` and `CampaignEventsFunction` (owner-authored email campaigns, sent through the separate campaigns AWS account, with their own queues, DLQs and alarms), `LifecycleScanFunction` (hourly EventBridge cron, FOUR independent guarded passes: the lead-age RULES drips, `runUsageNagScan`, the billing-rules scanner, and the opt-in weekly social-staleness digest), and `NotificationConsumerFunction` (`notificationConsumer.handler`, 256MB/30s, reserved concurrency 2; consumes `vivreal-notification-queue`, SQS batch-size-1, CFN-owned in THIS repo with its DLQ, queue URL exported for the cross-repo SSM handoff; resolves `pushsubscriptions`/`pushpreferences` against the main Vivreal DB via its own connection `src/notificationConsumer/db.js`, deliberately not `hbcreations/scripts/db.js`; sends web-push via VAPID. Ported from VR_Secure_API's `sendPushToGroup` with a fix: the original's inline `.catch()` made every send report fulfilled regardless of outcome. First producer: EventHandler's `markSiteLive`). Layout: `app.js` / `lambda.js` / `socket.js`, then `hbcreations/{api,services,models,scripts,config}` + `services/email/`, `emailConsumer/`, `lifecycleScan/`. (`src/stripe/` is long gone, no Stripe product routes here anymore.)

## Routes (highlights)

- Health: `GET /health`, liveness only, no I/O, and it reports the deployed commit as `release`. The old `src/helathCheckFns.js` (an unauthenticated endpoint that created and deleted production Cognito users, with three committed password literals) is DELETED; the literals remain in history and still need rotating (vivreal-hq `docs/projects/shipped-ledger.md`, 2026-09-22 evening).
- Auth: `POST /api/user` (signup), `/api/user/login`, `/api/user/loginSSO`, `/api/user/verifyEmail`, `/api/user/forgotUsername`, `/api/user/resendVerification`, `/api/user/requestPasswordReset`, `/api/user/resetPassword`, `GET /api/user/checkRegisterValue`. `/api/user/signUserOut` was removed in PR #34 (Main CLAUDE.md:164-168).
- Campaigns (public, token-gated): `GET/POST /api/campaigns/confirm` (confirms a person the owner added or imported, or a rejoin; site sign-ups are one step since v7.2 and never see it) and `GET/POST /api/campaigns/unsubscribe` (every matching row on the list, see v7 below).
- Demo-account claim (public, the token IS the auth): `POST /api/claim/verify` + `POST /api/claim/complete` (`services/claim/`, `verifyClaim`, `completeClaim`, `hashToken`, `changeClaimEmail`). Verify is **POST-only, reading `req.body.token`**, the 7-day claim token is an account-takeover credential that leaked into Sentry `request.url`/query_string/fetch-span `http.query` via the old GET `?token=`; GET was removed with NO alias. Claim email-change is rejected when another Cognito user holds that email, and **fails closed** when ListUsers truncates.
- Meta compliance: `POST /api/user/deauthorize/:provider`, `POST /api/user/data-deletion/:provider`, `GET /api/user/data-deletion/status` (bypass `handleHBRoutes`, scoped urlencoded parsers). Deauthorize/data-deletion now purge the tenant's Platform Data, match users by app-scoped user id, and replay requests that previously answered `no_data`. **The deauthorize path is destructive across tenants:** `removeMetaAccounts` pulls every account matching the Meta identity from up to `MAX_GROUPS_PER_CALLBACK` (10) groups, then has VR_CMS_API purge the synced posts and their re-hosted pictures (`src/hbcreations/api/users/metaCallbacks.js:137-242`). It fires when a Facebook user removes the Vivreal app with Meta's notify option on, so read `vivreal-social-sync` before anyone removes the app from a Facebook account that is connected to more than one Vivreal group.
- Email: `/api/sendSupportEmail` (the portal's Help form); `GET/POST /api/unsubscribe` (RFC 8058 one-click, HMAC token via `UNSUBSCRIBE_SECRET`).
- **`POST /api/sendContactUsEmail` DOES NOT EXIST. Deleted 2026-09-23, do not re-add it.** Its route, its mailer and its validator are all gone from `src/hbcreations/`, each replaced by a comment saying so. A site's contact form posts to VR_Client_API, not here. `sendSupportEmail` survives deliberately and is a different thing.
- The portal proxies only `user/login` + `user/ssoLogin` here (both manual cookie-setting routes).

## The templated-email spine

- ONE send entry point: `sendTemplatedEmail()` → template registry + shared layout → `queueEmail()` (SQS `vivreal-email-queue`) → EmailConsumerFunction sends via SES. LifecycleScan never sends directly, enqueue only. (Bypasses the legacy `sendEmailService.js`, which hardcodes `from` and drops `replyTo`.)
- Two categories: **transactional** (`Vivreal <hello@vivreal.io>`, config set `vivreal-transactional`, always sends, includes the `welcome` email fired on first verify/SSO login) vs **lifecycle** (`"Sam from Vivreal" <sam@mail.vivreal.io>`, replyTo hello@, config set `vivreal-lifecycle`, gated ONLY on the `suppressions` collection, NOT on the dormant `sendUpdates` flag).
- Lifecycle rules: every registered template declares a `status` (`cron`, `direct` or `parked` with a `parkedReason`), enforced at load by `templates/assertTemplateShape.js`; the default `LIFECYCLE_ACTIVE_RULES` is DERIVED from the `cron` set and a test fails if `sam-template.yaml` disagrees. **All twelve lifecycle templates are `cron` as of 2026-10-01**, nothing is parked (Main CLAUDE.md, Email Spine). An EMPTY `LIFECYCLE_ACTIVE_RULES` now means send nothing, and an unknown rule name is reported as `unknownRules` rather than silently disabling. Five billing rules are enabled and evaluate hourly against an empty cohort, because zero production groups hold subscription state; the run reports `billingCohort` so "no paying customers yet" and "the webhook writer broke" stop looking identical. Hourly scan, 2h-wide rule windows, dedupe makes overlapping passes no-ops. Deterministic holdout via sha256(email) mod 100 < `LIFECYCLE_HOLDOUT_PERCENT` (default 10).
- **Group-scoped quota-nag templates** `usage-near-quota` + `usage-over-quota` (registered in `templates/index.js`), fired by lifecycleScan's `runUsageNagScan`, free-tier only, dedupe on (groupID, level, month), `cron` like every other lifecycle template.
- **Social staleness digest** (fourth lifecycle pass, opt-in weekly): reads its cohort from `emaildigestpreferences` FIRST, mails only a channel this repo's copy of the fetch-health resolver (`services/social/fetchHealth.js`) calls `frozen`, reads `integrations[].accounts[]` only, deduped on (groupID, recipient, ISO week). See `vivreal-social-sync`. They greet by **groupName, not firstName**. The existing nudges above are untouched.
- **Billing-rules scanner (Phase 1)**, a THIRD engine in `LifecycleScanFunction`, because the leads RULES loop selects by `createdAt` age and dedupes on `templateId:email` permanently while billing events recur. Each billing rule supplies `episodeKey(group)`; dedupe key = `templateId:groupID:episodeKey`, so a new episode re-arms with no cron-side reset. **NO Stripe SDK in this Lambda by design**, every field read (`subscriptionStatus`, `subscriptionCadence`, `currentPeriodEnd`, `cancellation.*`) is written onto the group doc by VR_Secure_API's webhook handlers; if those stop firing, the rules go quiet rather than sending something wrong.
- **Phase 3 billing rules**: `cancel-confirmed` (in-app cancellations, sent BEFORE access lapses, carries the access-until date + undo; mutually exclusive with `subscription-cancelled-confirm` by construction; episode = `cancellation.requestedAt`, which `reactivateSubscription` nulls, so cancel→reactivate→cancel re-arms); `win-back-30d` (ONE email 30 to 60 days after access ended, free tier only, body matched to the exit-survey reason, the 60-day upper bound doubles as a first-run blast guard; `cancellation.feedback` is deliberately never merged into an email, only the survey KEY reaches the template); `annual-renewal-reminder` (CA ARL advance notice, 30-day lead, excludes already-cancelled plans, never held out, legal obligation; the renewal amount is wired into the notice). **Holdout policy:** account-state + legally-required emails opt out of holdout; only win-back permits a holdout arm.
- Idempotency is claim-first: `emailEvents` row (unique partial index on `dedupeKey` = `templateId:email`) inserted BEFORE enqueue; enqueue failure rolls back the claim.
- **Bounce and complaint events ARE wired (H105, closed 2026-09-21)**: SES to SNS `vivreal-email-events` to SQS `vivreal-email-events-queue` to `EmailEventsFunction`, which writes `hard_bounce`/`complaint` suppressions; soft bounces are counted, never suppressed. The configuration set is attached by the CONSUMER (`emailConsumer/lambda.js`), so no producer can send unattributed mail, and since 2026-09-22 no production path sends outside the queue. `vivreal-outreach` is deliberately NOT given a destination here (it is VR_Outreach_API's set). `MatchingEventTypes` is camelCase (`renderingFailure`) and CloudFormation does not validate it (Main CLAUDE.md, Email Spine).
- **Mail chrome comes from `@hillbombcreations/email-brand`, pinned EXACT** (`package.json:62`, 1.1.0 on 2026-10-04); this repo keeps no copy of its own.

## v7 to v7.2 (live 2026-10-20/21, tags v2.15.1 and v2.15.2)
- **Who still gets a confirmation email.** Site sign-ups are one step since v7.2 (VR_Client_API saves them `subscribed`), so the confirm link now serves two cases: people an OWNER added or imported (VR_CMS_API `importSubscribers` sends an intent) and an unsubscribed person who signed up again and was sent a rejoin email (VR_Client_API).
- **V7.221 subscriber confirmation, two functions.** `SubscriberConfirmFunction` (`src/subscriberConfirm/lambda.js`) consumes `vivreal-subscriber-confirm-queue` one message at a time and works one slice of a run; it is a plain handler that THROWS, so a bad message or a database fault goes back to the queue, `maxReceiveCount` and the DLQ alarm see it, and only settled outcomes return. `SubscriberConfirmResumeFunction` (`src/subscriberConfirmResume/lambda.js`, `cron(25 * * * ? *)`) re-enqueues due and silent runs and expires stale ones; it cannot send mail itself. Every decision is in `services/email/subscriberConfirm/{breaker,claim,intent,limits,processSlice,render,resume,runs}.js`. The intent shape (`intent.js`) is a hand copy of CMS's `SUBSCRIBER_CONFIRM_INTENT`, compared by vivreal-hq contract-drift.
- **Its ceilings and stops.** Daily ceilings per business and overall (`limits.js`, `DEFAULT_GROUP_DAILY`, `DEFAULT_GLOBAL_DAILY`, overridable by `SUBSCRIBER_CONFIRM_GROUP_DAILY` / `SUBSCRIBER_CONFIRM_GLOBAL_DAILY`); one re-ask per `OWNER_RESEND_COOLDOWN_MS` (`claim.js`, 7 days, which VR_Client_API's `REJOIN_COOLDOWN_MS` must equal); a GROUP breaker over this path's own sends for that business in the trailing 7 days and an ACCOUNT breaker at half of SES's review lines (`breaker.js`; a read failure pauses rather than proceeds). Read the thresholds there.
- **The confirm route** (`services/email/subscribeConfirm.js`) moves `pending` to `subscribed` only on a row with no `suppressedAt` whose address is not on the platform suppression list, and `unsubscribed` to `subscribed` only for a link issued after `unsubscribedAt`. A `bounced` or `complained` row is never moved. Its row filter is the address AND the list AND the business (`groupID` from the group document, never the token's spelling).
- **Unsubscribe and bounces move EVERY matching row (v7.2).** `campaignUnsubscribe.js` is an `updateMany` over `{ groupID, 'collectionObj.refID', subscriberEmail }` that skips rows already `unsubscribed` (so a second click keeps the original `unsubscribedAt` the rejoin cooldown reads); it answers `already` when every row was unsubscribed and `not-found` only when there is no row at all. `src/campaignEvents/lambda.js` suppresses bounced and complaining addresses with `updateMany` scoped to the campaign's list and its `groupID`; a campaign whose `groupID` differs from the event's group suppresses nobody and is reported (`campaignEvents.group_mismatch`, plus a Sentry message carrying ids only). The reason: `collection_objects` is shared by every group on a pod, and one list can hold the same address twice, which `sendBatches` mails twice.
- **Pushes are split by surface (v7).** `notificationConsumer` sends staff (pinned-recipient) types only to subscriptions with `surface: 'admin'` (the admin app's devices) and customer types only to the rest, and logs `no-subscriptions` when a staff push has no admin device (`src/notificationConsumer/lambda.js`; `surface` is declared in `db.js` so `strictQuery` keeps the filter). See `vivreal-infra:vivreal-notifications`.

## Patterns

- **Handler → Service → Model.** API layer Joi-validates, calls service, sets `req.resData = {status, response}`. `handleHBRoutes()` connects DB, runs handler, catches errors. 500s never leak stack traces.
- Auth flow: signup, Cognito `SignUpCommand`, verify, then login returns JWTs. Login (standard and SSO) mints `ctxPayload.dbKey` by **reading the stored placement**: `resolvePlacement(group)` from `@hillbombcreations/tenant-db/placement`. There is no tier mapping and no fallback. A group projection that drops `dbKey` makes it THROW rather than silently reroute, which is the entire point of the package. `deriveDbKey()` is deleted. If you find it, or `databaseDict[group.tier]`, or any inline tier-to-database ladder, that is the bug, not the pattern.
- **featureFlags now returned in the login group payload**, it was missing from `handleSettingUpGroups`' per-group whitelist, so `AuthContext.groups` arrived with `featureFlags` undefined on every login and every client-side gate evaluated false (`useAgentAccess`, the AI assistant was invisible to EVERY group, including Mongo-enabled ones; the Group-page toggle only appeared to work because it patched AuthContext in-session). Both projections fixed (`userLoginService` + `userLoginSSO`).
- Models: `inquiries`, `groups` (now from `@hillbombcreations/schemas`), `leads`, `emailEvents`, `suppressions`, `dataDeletionRequests`, claim tokens (`claimTokenSchema`).
- **Quota gates (`@hillbombcreations/tier-quotas`)**: `handleSettingUpGroups` (login bootstrap) serializes entries/seats/apiCalls/cdnBytes from `getTierQuotas(tier)`. `addUserToGroup` + `checkRegisterValue` (signup seat gate) check **package seats with a >0 sentinel guard**, a bare `>=` against enterprise `seats: -1` would block every join. **Stored-value-wins** for seat/entry quotas (grandfathering) with tier-default fallback; api/cdn quotas are package-authoritative. `isUnlimitedQuota` v3 = `value < 0` and needs its `=== 0` guard so free-tier `agentActions: 0` doesn't divide-to-Infinity into a spurious over-quota nag.
- **Owns the `leads` collection** in mainDb `Vivreal`. Lifecycle fields `activated`/`activatedAt` are written CROSS-SERVICE by VR_CMS_API (first content create) and VR_Secure_API (site launch); join key = lowercased email. Beware: Mongoose setters don't apply to query filters, lowercase emails yourself in filters.

## Gotchas

- **`errorHandler` is correct only in CONTROLLER position** (it sets `req.resData` and always calls `next()`): router-level middleware must write its own response, or the gate fails OPEN while still logging (VR_Client_API's `frozenCheck` once served frozen accounts a 200 this way). Test a gate by the status on the wire, never by "errorHandler was called".
- **A handled 4xx/5xx is a SUCCESSFUL Lambda invocation** under serverless-express, so `AWS/Lambda Errors` never moves. Alarm on a log literal the code emits on every failure exit, paired with an API Gateway 5xx alarm for throttled requests that never ran.
- **CORS is wide open** (`callback(null, true)`), intentional for the public API.
- **Mongo is one client per process now**, built by `@hillbombcreations/tenant-db`'s `createMongo` (`src/shared/mongo.js:4`, `appName: 'VR_Main_API'` at `:40`) and shared by `scripts/db.js`, `services/campaigns/campaignDb.js` and `notificationConsumer/db.js`; tenant databases are `useDb` views, with no eviction on `readyState` (`src/hbcreations/scripts/db.js:1-17`). The old `maxPoolSize=10` figure is gone: no `maxPoolSize` literal remains under `src/`, so read the pool from the package default. See `vivreal-atlas-topology`.
- **Secrets Phase 2 is done**: every Lambda resolves config via CloudFormation dynamic references from `<secret-prefix>/main-api` + `<secret-prefix>/stripe` + `<secret-prefix>/social-oauth` (Secrets Manager) and SSM `<ssm-prefix>/*`, **any `hb-api-secrets` reference is now wrong**. The old hardcoded Stripe live key (`createUserService.js`/`checkUserExistsEmail.js`) and repo-root `googleAppJSON.json` are gone.
- arm64-only Lambda layers (x86_64 extension → `Extension.Crash`).
- Coverage gate: 100% lines/statements/functions, 85% branches.
- **errorHandler forwards `err.code`** as `errorCode` on non-5xx responses. Error bodies here are **bare JSON strings**, not the standard `{success,data}` envelope, the portal's manual `user/login` route now unwraps them via `extractUpstreamError()`/`extractUpstreamDetail()` (login error branches like badUsername/incorrectPassword were DEAD in prod before this).
- **Two auth bypasses closed**: quota seat gates now DENY on a 0-seat quota instead of admitting everyone (was fail-open); the Meta callback auth gate's prototype-key bypass is closed (`provider='toString'` used to resolve to `Object.prototype.toString`).
- ESLint adopted + a husky pre-push gate (lint, then `nyc` against `package.json`'s declared thresholds); the temporary `.coverage-floor.json` ratchet was deleted once the thresholds were met. No GitHub Actions test workflow exists here, so the hook is the only automated gate before merge (Main CLAUDE.md, The gate).
- ⚠️ **Tests can send REAL emails**, `queueEmail` is not stubbed in the test suite; never run the full suite against a prod `.env` (this has fired ~140 real sends before). Never copy a prod `.env` into a backend test worktree.
- The consolidated prod-bug punch list (portal + all backends, fixed vs still-open) lives at `Vivreal_Portal_Mobile/docs/projects/portal-frontend-testing-strategy/prod-bugs-found.md`.

## Lambda and MongoDB checklist (ported from the `main-api` expert agent, 2026-10-20)

The expert agents are no longer loadable as skills, so the review checklist an agent without an
`Agent` tool used to load from them lives here. Query rules (tenant scoping, the mainDb `_id`
lookup, the `publishDate` and `archived` filters) live in `vivreal-knowledge:vivreal-db`, and
packaging and limits in `vivreal-infra:vivreal-lambda`; they are not repeated here.

### AWS Lambda best-practice alignment

- Reuse SDK clients across invocations (`aws-sdk` v3 clients should be top-level, not per-handler).
- Cold-start: every function is its own cold-start path, don't share global state across them. **No aliases in this stack**: API Gateway invokes the function directly, so `$LATEST` IS production here (the opposite of VR_Secure_API's HTTP functions).
- Bundle size: webpack should tree-shake `aws-sdk` v3 modular imports. Verify the build output.
- Memory: Express Lambda runs at 1024 MB by default, flag any `Buffer` allocations in request paths.
- Timeout: Cognito verification can hit 30s timeout under JWKS rotation, ensure retries with exponential backoff.

### MongoDB consistency & performance

- Write paths: user creation (verify it uses `findOneAndUpdate` with `upsert: true` and `setOnInsert` to avoid race conditions on duplicate signups), the email spine (`emailEvents` claim-first inserts, `suppressions`, `leads`), and the claim flow (`claimTokenSchema` model, `services/claim/`).
- No multi-document transactions are needed, flag any unnecessary `session.startTransaction()` calls.
- Index audit: `email`, `cognitoSub`, `stripeCustomerID` should all be unique-indexed.
