### Known gotchas
- Many separate Lambdas (count them from `allRoutes.yaml`); cross-Lambda invocation is async, never assume warm coordination.
- **Two Cognito pools, and an HTTP route binds to ONE.** The five `/api/admin/*` routes (`getGroupInformation.yaml`) use `MyAdminCognitoAuthorizer`, the dedicated admin pool (`Vivreal-Admin-Identity`, MFA), so a customer-pool token is rejected at the gateway there; `PUT /api/group/featureFlags` accepts EITHER pool. Every other route inherits `DefaultAuthorizer` (the customer pool). The operator console is the internal admin app (`vivreal-hq/packages/admin-app`); the portal's feature-flag console and admin analytics surfaces are deleted.
- **Ctx tokens are audience-bound (H6006, 2026-09-27).** Each service verifies with a key DERIVED from `CTX_SECRET` (`HMAC(CTX_SECRET, 'vivreal/ctx/v2/<service>')`) and checks `aud`; the admin gate requires `exp` and accepts only tokens addressed to this service. A token minted for one service is not valid at another, so a hand-minted test token must name the right audience.
- **Site-manager gate on destructive site and domain routes.** `withSiteRole(...)` wraps them at route registration in `src/createSites/api/index.js` (delete site, deploySite, instantiateTemplate, rename subdomain, custom-domain connect and remove, domain order and cancel, attach, detach, transfer in, transfer out and its cancel, registrant read, renewal switch). Read the file for the current set; it is selective, not blanket. ### Site page routes (v6, v2.21.5)
- Four routes on UpdateGroup: `POST /api/site/pages` (add), `PUT /api/site/pages/reorder`, `PUT /api/site/pages/{pageSlug}` (update), `DELETE /api/site/pages/{pageSlug}`. The `/api` prefix is required: the Express router mounts `/site/pages...` but the gateway declares `/api/site/pages...`. Each reads the site PROJECTED and lean, scoped by `{ _id, groupID }` (an unprojected read of the 729 KB vivreal.io site cost about 7.5 s). Add requires `order` and accepts no `blocks`, so an API-added page renders empty until an update writes them.
- **The update allow-list is built from the schemas package's `pageFields`** (`updatePageValidator`, `updates` keys), the union of every key stored on a prod page. A new page field needs a line in `pageFields` and nowhere else. Send each touched top-level page field WHOLE (`hero`, `labels`, `blocks`, `cta`): the service writes `pages.$[elem].<key>`.
- **One page order rule** (`src/shared/pageOrder.js`): `order` is an integer `>= -1`, used by add, update, `/sites/update` and both site-create paths. `-1` is the home page sentinel the portal's `recomputeOrder` pins. PageSchema declares `order: Number` (the v6 schemas minor), so junk would be a CastError 500; every path refuses it as a 400 instead.
- **Reorder now persists** (`bulkWrite` of `pages.$.order` = position + 1; the write was stripped before the schema declared the key), refuses an unknown slug with 404 before any write, and returns only slugs and orders. **No caller exists today** in the portal's `src` (`origin/stable` and `origin/main`), VR-MCP-Server or Vivreal_Site_Migrator (a grep for `pages/reorder` finds only a portal ecosystem doc).
- **Known trap, fix on the next list: the reorder route's error path falls through.** Its controller calls `errorHandler(...)` from controller position, and `errorHandler` always calls a plain `next()`. Express then matches the NEXT route, `PUT /site/pages/:pageSlug`, with `pageSlug = "reorder"`, so a refused reorder runs the page-update handler. Until it is fixed, assert the status a reorder refusal puts on the wire, and do not add a caller that trusts a reorder error.

### Write-path traps
- **Dotted and `$` body keys never reach a handler.** The global sanitizer drops any body key containing `.` or starting with `$`, so `updates: { 'hero.title': ... }` arrives as `{}` and the update 500s on an unused array filter. Send whole top-level fields.
- **`updateSiteValues` MERGES `siteDetails.values` now:** an absent key is untouched and an explicit `null` clears it ("THE WRITE CONTRACT" at the top of the file). It replaced the `PRESERVE_ON_REPLACE` allowlist, which failed four times (share image, logo, redirects and `lifecycleState`, `businessInfo`) because a list only covers the keys it was written for. Its unconditional `domainInformation` `$set` is safe only because Mongoose strips `undefined` during cast. After any site write, re-read the whole document and diff it against a pre-write backup.
- **An undeclared tenant-db model is `undefined`, not unbound.** Each Lambda's main-db map declares its own models (`instantiateTemplateWorker` declares only `siteTemplates`), so `mainDb.DB.groups` there is a `TypeError`. A mock carrying both models passed 100% coverage over a line that could never run. Read the worker's own models map before adding a `mainDb.DB.<model>` call, and assert `Object.keys(mainDb.DB)` against the REAL map in a test.
- **`errorHandler` is correct only in controller position** (it always calls `next()`; see the reorder trap above). Router-level middleware writes its own response. `handleHBRoutes` documents the same rule at its two refusal paths.
- **A handled 4xx/5xx is a SUCCESSFUL Lambda invocation** under serverless-express, so `AWS/Lambda Errors` never moves. Alarm on the `<Function>.failed` literal `errorHandler` emits on every handled 5xx, paired with an API Gateway 5xx alarm for requests that never reached the code (throttles log nothing).

### AWS Lambda best-practice alignment
- One deploy artifact per function, each with its own CloudFormation fragment and its own `build-lambdas.js` roster entry; a function missing from the build roster fails packaging, not tests.
- Stripe SDK initialization must be top-level, reused across warm invocations.
- IAM least-privilege: each Lambda must have only the policies it needs.
- WebSocket: agent, createAndJoinGroup, createSites and updateGroup carry `WS_ENDPOINT` + `WS_TABLE`. Send-message paths must be idempotent on stale connections.
- Step Functions integration: use `StartExecution` ARN format, NOT `DescribeExecution` ARN format (different IAM resource types).
- Cold start: billing Lambda's webpack bundle is the largest (Stripe SDK is heavy), measure and consider Provisioned Concurrency if p99 cold-start exceeds 3s.

### MongoDB consistency & performance
- mainDb queries: ALWAYS `{ _id: ObjectId(groupID) }` (shell form; in Node write `new ObjectId(groupID)`, bson 6 throws without `new`). NEVER `groupName`. `{ key }` takes the group's slug, never `dbKey`: `dbKey` is the tenant database name (`pod_01`, `pod_02`), no group's `key` equals it, so `{ key: dbKey }` returns null.
- `dbKey` is the tenant DATABASE name stored on the group document, and nothing else. It is not `group.key`, which is the slug.
- **The S3 bucket is `bucketOf(group)`** (`src/shared/groupBucket.js`): the stored `group.bucket` wins, else `${group.type}-${group.key}`, and it THROWS when neither exists rather than touching `undefined-undefined`. New groups get `bucket` at creation, named from a pre-generated `_id`. Never assume a `vivreal-` prefix. It is for S3 only, never DB routing.
- Profile switch atomically updates `activeGroupID` on the user doc and re-issues the `active_ctx` JWT, verify the order doesn't leak across requests.
- Group creation: insert + S3 bucket creation must roll back together on partial failure (idempotent retry).
- Index audit: `groupID`, `userID`, `stripeSubscriptionID`, `cognitoSub` must be indexed; `groupID + userID` compound index for membership queries.
