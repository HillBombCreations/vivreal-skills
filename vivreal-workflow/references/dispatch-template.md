Every dispatch: (1) ONE repository per coder or portal-coder dispatch; several repos means several dispatches. (2) The base or head SHA, pinned (`origin/main@<sha>`), and the `model` from the live values printed at session start (owner rule P-model). (3) The spec file path when one exists; a design, review or walk brief that touches a portal or customer-site screen also names the owners' UI rules, `vivreal-knowledge:vivreal-portal-knowledge` `references/ui-rules.md`, and what that agent owes against them (release-conductor section 3, L-B-46), while a regular-user brief never names them. (4) The mode, for portal-coder. (5) The exact commands it may run and the test scope; every WSL step in them starts by changing into the worktree inside one quoted login-shell command (`wsl.exe -e bash -lc 'cd /mnt/<drive>/<clones>/_wt/<worktree> && <command>'`), because a bare `wsl` call runs in whatever folder the shell is in, often an owner's own checkout, a plain `bash -c` runs the Windows npm, and without `-e` an outer shell expands every `$` in that folder first; a long step goes in a script file, and a worktree WSL git cannot read is tested in a clone made from a `git bundle` on WSL's own disk, never by an install on Windows instead (`vivreal-workflow/skills/shared-standards/references/wsl.md`). (6) Full scope and authority in the first prompt; a GO is quoted verbatim with name, time and source: `GO: "<exact words>" from <Justin|Hunter>, <ISO time>, <source>`. The name is the owner who gave it, read from the session's `gh` login and mapped by P-go-form (`vivreal-workflow:release-conductor` section 4); only another login, or none, asks "Who is giving this go, Justin or Hunter?" in the same question; never infer it from the Claude account, an account email or git config, the time is exact (`date -u +%Y-%m-%dT%H:%M:%SZ` run right after the answer, never "about 17:25Z"), and it sits in the FIRST prompt of a fresh dispatch; the release engineer refuses anything less, which cost two round trips on 2026-11-04. (7) Verified premises only: read the deployed validator or release line, not main. Code reads in vivreal-hq name a kept hq worktree (`$VIVREAL_REPOS/_wt/hq-main`), never the hq clone, which IS an owner's own checkout: a brief saying to read code with `git -C "$VIVREAL_REPOS/<repo>" ...` sent three agents' hq reads there on 2026-11-20 (L-B-45). Since F641 the same holds for every repo: the brief names a worktree under `$VIVREAL_REPOS/_wt/` for each repo it touches (the main thread makes one when none exists), and the owner-checkout guard refuses a subagent's command in a clone at the root. (8) Report at most 250 words, ending with any `Needs:` line. (9) Done means pushed, with a PR URL in the report (vivreal-skills: committed on a local branch, with the branch and head in the report, one PR per batch, pushed only when ready to merge, P-skills-push-after-review) (or the pushed head SHA in a no-PR mode). No skill or review runs as the last step.

Two traps around a dispatch. Preparing is not dispatching: after an environment readiness report, launch the agent that uses it in the same turn. Never tell a coder to "consult an expert": that consumes the coder's own task; name the knowledge skill it should load instead.
